# Навантажувальне тестування

## Сценарій

Файл `loadtest/notes.js`, інструмент k6.

Профіль «мало записів, багато читань». Кожен віртуальний користувач у циклі виконує:

1. `POST /notes` — створює нотатку від свого імені (`user-<номер>`);
2. 9 читань:
   - 4 × `GET /notes` — список останніх 50 нотаток;
   - `GET /notes/{id}` — щойно створена нотатка;
   - 3 × `GET /notes/{id}` — випадкові нотатки зі списку;
   - `GET /authors/{author}` — дані автора (кількість нотаток, час останньої);
3. пауза 1 с.

Співвідношення запис : читання = 1 : 9.

Фази:

| Фаза | Тривалість | Користувачі |
|---|---|---|
| Наростання | 2 хв 30 с | 0 → N |
| Стале навантаження | 5 хв | N |
| Спад | 2 хв | N → 0 |

Разом 9,5 хв.

## Запуск

Встановити k6: `winget install GrafanaLabs.k6`. Потім з кореня репозиторію:

```
k6 run -e BASE_URL=http://<адреса ALB> -e USERS=40 -e RESULT=cache-on loadtest/notes.js
```

Адреса береться з `terraform -chdir=infra output public_url`. Усі параметри описані в `loadtest/README.md`.

## Підбір N

Одна копія має 0.25 vCPU. N підбирали пробними запусками так, щоб на сталому навантаженні середній CPU перевищив 60% і з'явилася хоча б одна нова копія, але частка помилок лишалася нижчою за 1%.

Пробний прогін: N = 20, розгін 1 хв, стале навантаження 3 хв. Одна копія дійшла до 97–99% CPU, ~98 запитів/с, 0% помилок, p95 = 124 мс. Цього вистачило, щоб автомасштабування додало другу копію, тож більше N не потрібне: при більшому N одна копія перевантажилась би ще до появи другої, і зросли б латентність та помилки.

Обрано **N = 20**.

## Висновки

- Сервіс витримав 20 користувачів без жодної помилки. Масштабування додало другу копію на 6-й хвилині прогону.
- p50 і p95 низькі, а p99 майже втричі більший за p95. Найповільніші запити припадають на хвилини 20:13–20:17, коли одна копія працювала на 92–96% CPU і запити чекали в черзі. Після появи другої копії латентність повернулась до норми. Максимум 4,3 с — поодинокий запит саме в цей час.
- Середнє за весь прогін (88 запитів/с) нижче за піковий потік, бо в нього входять фази розгону і спаду. На сталому навантаженні було ~120 запитів/с (~7 тис. за хвилину на панелі).
