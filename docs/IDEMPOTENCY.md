# Ідемпотентність операцій запису

## Яку проблему це розв'язує

Клієнт надіслав `POST /notes`, а відповідь не дійшла: обірвався мобільний інтернет, спрацював таймаут на балансувальнику чи в клієнті, копія застосунку була вилучена масштабуванням. Клієнт не знає, чи нотатку створено. Якщо він повторить запит, може з'явитися дубль. Якщо не повторить — запис може бути втрачено.

`GET`, `PUT`, `DELETE` ідемпотентні за визначенням HTTP: повтор не змінює результат. `POST` — ні, кожен виклик створює новий ресурс. Заголовок `Idempotency-Key` робить `POST` безпечним для повторів: клієнт генерує унікальний ключ (UUID) на одну логічну операцію і надсилає його з кожною спробою.

## Як працює

Код у `app/main.py`, функції `idempotency_start` і `idempotency_finish`:

1. Перший запит з ключем атомарно ставить у Redis `SET idem:<ключ> {"state":"pending","hash":...} NX EX 86400`. `NX` гарантує, що з двох одночасних запитів з тим самим ключем виконуватиметься лише один.
2. Операція виконується, і результат (код відповіді + тіло) зберігається під тим самим ключем на **24 години**.
3. Повторний запит з тим самим ключем не виконує операцію, а повертає збережену відповідь з тим самим кодом і заголовком `Idempotent-Replayed: true`.
4. Особливі випадки:
   - той самий ключ, але **інше тіло запиту** → `422`. Порівнюється SHA-256 тіла, щоб помилка клієнта (один ключ на дві різні операції) не віддала чужий результат;
   - повтор, поки перший запит **ще виконується** → `409 Conflict`, клієнт повторить пізніше;
   - якщо операція **впала з помилкою**, ключ видаляється, і клієнт може спробувати ще раз.

Без заголовка `Idempotency-Key` запис працює як раніше.

## Як поєднується з чергою (завдання 6)

Ідемпотентність потрібна на **двох рівнях**, і вони доповнюють один одного:

| Рівень | Від чого захищає | Механізм |
|---|---|---|
| Клієнт → API | клієнт повторив запит, бо не отримав відповідь | `Idempotency-Key` у Redis: повтор не кладе друге повідомлення в чергу, а повертає той самий `202` з тим самим `job_id` |
| Черга → обробник | SQS доставив повідомлення двічі («щонайменше один раз») | `job_id` → `notes.request_id UNIQUE` + `INSERT ... ON CONFLICT DO NOTHING` |

Для асинхронного запиту `job_id` обчислюється з `Idempotency-Key` (перші 32 символи SHA-256). Тому навіть якщо запис у Redis пропаде (наприклад, Redis перезапустився), повторний запит з тим самим ключем створить повідомлення з тим самим `job_id`, і база відкине дубль. Ланцюжок «клієнт → API → черга → обробник → база» ідемпотентний від кінця до кінця.

## Обмеження

- Redis у нас без збереження на диск. Якщо контейнер Redis перезапуститься, збережені відповіді зникнуть. Для синхронного запису це означає можливий дубль, якщо клієнт повторить запит саме після перезапуску. Для асинхронного запису дубль усе одно відсіче унікальний `request_id` у базі. У продакшені варто використовувати ElastiCache з реплікою або зберігати ключі ідемпотентності в самій базі в тій самій транзакції, що й запис.
- 24 години — компроміс: досить довго для будь-яких автоматичних повторів, але не безкінечно займає пам'ять.
